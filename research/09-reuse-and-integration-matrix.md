## 2. Foundation designs compared

Four ways to build F1:
- **A. OpenBot as the foundation.** Fork it, set the policy to deny, and add a repro Bot.
- **B. OpenMuse as the foundation, plus a stronger sandbox.** Fork it, move Docker behind a supervisor, and add runsc and egress.
- **C. A minimal new app with ported patterns.** Our own API, UI, DB and supervisor. Patterns come from both repos; no code is imported unless noted.
- **D. Protocol-level integration of both.** Run OpenBot and OpenMuse side by side and bridge them via AG-UI or the OpenMuse `OpenBotAdapter` (which is DISABLED: `packages/backends/src/openbot.ts:139-141,245-254@205cc38`).

### 2.2 Verdict

**Best buildable in about 24 h: C.** The expected conclusion holds after verification. The deciding facts:
1. **Both** foundations hard-require a closed, externally hosted CopilotKit Intelligence service at startup. We confirmed this in code today (§0 table). That puts conversation data off Vultr and adds an account dependency on event day.
2. OpenBot's agent executes computer tools in the browser tab, which is the wrong trust location for server-enforced approvals.
3. OpenMuse runs Docker from the API process.
4. The assets we actually want are small: OM approval + lease + receipt + flags (~500 LOC of patterns), and OB supervisor shape + audit-before-act (~300 LOC). Porting them is cheaper than neutralizing either codebase.

**Best long-term: still C,** with two conditions:
- Keep our event schema AG-UI-shaped, so a later AG-UI endpoint can plug C's verifier into OpenBot as a remote Bot or into any AG-UI client without sharing its identity or DB.
- Keep the supervisor API stable, so a microVM or throwaway-VM backend (13 §4 C/D) can replace runsc.

B is the runner-up long-term, but **only if** CopilotKit Intelligence becomes optional or self-hostable under a free license. OM's durability and approval discipline is the closest philosophical match. A becomes attractive only for a multi-tenant "coworker" product with SSO and MCP, which F1 is not. D is not recommended at any horizon: it duplicates runtimes, DBs, identity and thread stores and has no benefit for F1.

**Contrary evidence considered:**
- (i) OB/OM have 349 and ~154 upstream tests (07 §1; 08 §11), and we would forgo that coverage. We mitigate by porting the *test cases* for approval and lease semantics as our T-APR / T-RUN suites.
- (ii) CopilotKit React could give a nicer chat UI fast. F1 doesn't need chat, and the banned "dashboard-as-main-feature" risk (01 §4) is unaffected either way.
